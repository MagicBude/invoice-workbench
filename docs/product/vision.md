# 产品愿景与定位

## 1. 产品定位

Invoice Workbench 是一个专注于 **PDF 发票批量整理与结构化导出** 的 Web 工具。

产品层保持垂直：优先把发票整理做稳定、做顺手。

技术层保持可扩展：底层解析、校验和文档处理能力尽量模块化，为未来扩展其他结构化文档处理能力保留空间，但不在早期稀释产品焦点。

## 2. 核心用户问题

典型场景是：用户手里有几十到几百份 PDF 发票，需要整理成表格，人工逐份打开并复制以下数据：

- 日期
- 名称
- 发票号码
- 不含税金额
- 税额
- 价税合计
- 开票日期
- 销售方 / 购买方信息
- 其他用于报销、归档或统计的字段

手工流程慢、容易遗漏，也难以发现重复发票与金额异常。

## 3. 核心价值

Invoice Workbench 将流程变成：

```text
拖入 PDF
→ 自动解析
→ 自动校验
→ 人工快速复核
→ 自定义导出字段
→ Excel / CSV
```

重点不是“AI 炫技”，而是减少重复劳动，并让结果可追溯、可修正、可导出。

## 4. 产品原则

### 专注发票，而不是一开始做通用 PDF 平台

“任意 PDF 自动提取任意信息”的范围过大，会把问题扩展到合同、简历、银行流水、扫描文档、表格等完全不同的版式。

第一阶段只把发票做到稳定、可用、可维护。

### 本地优先（Local-first）

发票包含公司名、税号、金额等敏感数据。标准电子发票通常自带文本层，因此大量处理可以直接在浏览器完成。

默认不上传原始 PDF 是产品价值的一部分，而不仅仅是技术实现细节。

### 必须可复核

任何自动解析都可能出现异常，因此产品不能只有“识别成功 / 失败”。

必须允许：

- 查看原文件名
- 修改解析结果
- 显示异常原因
- 标记低置信度结果
- 后续实现 PDF 与字段并排复核

### 导出内容必须可配置

不同用户的报销或统计模板不同，因此导出字段必须可选。

用户可以只导出：

```text
日期 + 名称 + 发票号 + 价税合计
```

也可以导出完整字段集。

## 5. 产品边界

v0.1 不试图解决：

- 发票真伪查验
- 税务合规判断
- 税务申报
- 企业 ERP
- 完整财务系统
- 任意文档理解

## 6. 长期方向

当发票整理闭环成熟后，底层能力可以逐步扩展为结构化文档处理核心，例如：

```text
文档处理核心
├── 发票解析器
├── 收据解析器
├── 流水解析器
└── 合同解析器
```

但对外产品是否扩展，应由真实用户需求决定，而不是为了技术通用化而通用化。
