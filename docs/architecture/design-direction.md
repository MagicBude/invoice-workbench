# 技术方向与设计取舍

本文记录 Invoice Workbench 当前已经明确的关键技术方向，作为后续开发时的长期约束与判断依据。

## 1. 浏览器本地处理作为默认主路径

标准电子发票通常包含可读取的 PDF 文本层，因此第一阶段优先采用浏览器本地处理：

```text
文件 → ArrayBuffer → PDF.js → getTextContent() → 文本
```

这样可以同时获得几个明显优势：

- 原始发票默认不离开用户设备
- 不依赖服务器上传与存储
- 标准电子发票处理速度快
- 基础使用几乎没有后端运行成本
- GitHub Pages 即可部署第一阶段产品

## 2. PDF.js 负责读取，invoice-core 负责理解

PDF.js 的职责是把 PDF 文本层读取出来，不负责具体业务字段判断。

真正的发票业务规则应集中在：

```text
packages/invoice-core
```

这样可以避免把正则、金额规则和状态判断散落在 React 页面中，也方便后续增加测试样本和替换具体实现。

## 3. 文件名是辅助信息源，不是发票正文的替代品

用户实际整理文件时，文件名往往已经包含日期、简称或金额。

因此项目允许从文件名解析辅助字段，例如：

```text
2026.08.14-京东-128.50元.pdf
```

但必须明确区分：

```text
文件名日期 / 文件名名称
```

与：

```text
开票日期 / 销售方名称 / 购买方名称
```

文件名数据可以用于辅助整理和交叉校验，但不能覆盖发票正文中的正式字段。

## 4. Excel 与 CSV 尽量在浏览器本地生成

导出属于本地数据整理的一部分，没有必要为了生成一个 Excel 文件再引入服务器。

v0.1 采用浏览器直接生成 Excel / CSV，并且：

- Excel 与 CSV 使用同一份字段注册表
- 用户可以自由勾选导出列
- 后续可以增加列排序与导出模板

## 5. 自动解析结果必须允许人工修改

自动识别不是最终事实。

因此表格必须可编辑，并逐步增加：

- 缺失字段提示
- 校验异常提示
- 低置信度高亮
- PDF 与结构化字段并排复核

产品目标是“减少人工抄录”，不是“禁止人工确认”。

## 6. 启发式规则只能作为兜底

例如：

```text
最大金额 → 价税合计
最小金额 → 税额
```

这类规则对简单票据可能有效，但面对多税率、折扣、负数或红字发票时并不可靠。

长期解析优先级应保持为：

```text
明确标签
→ 上下文 / 位置关系
→ 启发式兜底
→ 数学校验
```

未来加入 OCR / AI 后，也应放在本地规则之后，而不是替代本地规则。

## 7. 浏览器本地只持久化必要偏好

v0.1 可以使用 `localStorage` 保存：

- 导出列选择
- 非敏感界面设置

默认不保存：

- 原始 PDF
- PDF 全文
- 发票敏感字段历史

如果未来使用 IndexedDB 保存任务现场，必须同时提供明确的数据清除入口。

## 8. 第一阶段保持静态应用

v0.1 使用 Next.js Static Export 与 GitHub Pages，避免过早引入：

- 后端服务器
- 数据库
- 对象存储
- 登录系统
- 文件任务队列

等本地工作流稳定后，再根据 OCR、AI、云端历史和团队协作等真实需求加入后端。

## 9. 长期目标

当前最重要的不是一次性覆盖所有发票格式，而是建立一套可持续扩展的解析体系：

```text
输入
→ 文本获取
→ 标准化
→ 字段提取
→ 校验
→ 置信度
→ 人工复核
→ 自定义导出
```

后续每增加一种发票版式，尽量通过新增规则和测试扩展，而不是修改出一套无法解释的全局特例。
