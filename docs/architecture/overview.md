# 总体技术架构

## 1. v0.1 总体架构

```text
                         浏览器
┌─────────────────────────────────────────────────────────┐
│ Next.js 静态应用                                        │
│                                                         │
│  File API                                               │
│     ↓                                                   │
│  PDF.js                                                 │
│     ↓                                                   │
│  提取文本                                               │
│     ↓                                                   │
│  @invoice-workbench/invoice-core                        │
│     ├── 文本标准化                                      │
│     ├── 文件名解析                                      │
│     ├── 发票字段解析                                    │
│     ├── 数据校验                                        │
│     ├── 重复检测                                        │
│     └── 导出字段注册表                                  │
│     ↓                                                   │
│  可编辑表格                                             │
│     ↓                                                   │
│  SheetJS / CSV                                          │
│     ↓                                                   │
│  本地下载                                               │
└─────────────────────────────────────────────────────────┘

                     v0.1 不需要后端
```

## 2. 为什么第一阶段不先做 FastAPI

标准电子 PDF 发票通常已经包含文本层。

对于此类文件，浏览器可以直接读取文本，不需要：

- 上传原始文件
- OCR
- 后端 CPU
- 对象存储
- 文件清理任务

因此在 v0.1 阶段，引入后端带来的复杂度大于收益。

## 3. 为什么仍然保留未来后端方向

浏览器本地解析无法覆盖所有情况，例如：

- 扫描件
- 图片 PDF
- 极端版式
- 需要大模型推理的模糊字段
- 企业云端历史记录
- 团队协作

因此未来架构遵循：

```text
本地解析优先
       ↓ 失败或低置信度
用户主动选择云端处理
       ↓
OCR / AI API
       ↓
结构化结果
```

## 4. 模块边界

### Web 应用

路径：`apps/web`

负责浏览器 API 与用户交互，不承担复杂业务规则。

### 发票解析核心

路径：`packages/invoice-core`

使用纯 TypeScript，实现可测试、可复用、尽量无浏览器依赖的核心逻辑。

未来加入 FastAPI 后，可以再评估：

- 继续由前端使用 TypeScript 核心
- 后端实现同等解析规则
- 或把关键规则抽象为跨运行时方案

v0.1 不提前解决尚未出现的复杂问题。
