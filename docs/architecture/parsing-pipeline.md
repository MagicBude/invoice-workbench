# 发票解析流水线

## v0.1 流程

```text
PDF 文件
   ↓
校验文件类型
   ↓
PDF.js getTextContent()
   ↓
normalizeInvoiceText()
   ↓
parseFilenameMetadata()
   ↓
detectInvoiceType()
   ↓
字段提取器
   ├── 发票号码
   ├── 开票日期
   ├── 销售方 / 购买方
   ├── 金额
   ├── 税率
   └── 项目名称
   ↓
validateAmountRelation()
   ↓
重复检测
   ↓
置信度与解析状态
   ↓
InvoiceRecord
```

## 1. PDF 文本层优先

PDF.js 使用 `getTextContent()` 获取每页文本。

这是标准电子发票的主处理路径。

如果提取结果几乎为空，应判断为：

```text
NO_TEXT_LAYER
```

而不是继续用大量正则强行猜测。

## 2. 文本标准化

建议统一处理：

- 全角数字 → 半角数字
- 特殊“月 / 日”Unicode 变体
- 连续空格
- 不同冒号形式
- 金额千位分隔符
- 常见人民币符号

## 3. 金额解析层级

不要长期依赖“最大金额就是价税合计、最小金额就是税额”这样的简单规则。

推荐优先级：

### 第一级：明确标签上下文

例如：

- 合计
- 税额
- 价税合计（小写）

### 第二级：位置与邻近文本

通过 PDF 文本项坐标增强字段与金额之间的关联。

### 第三级：启发式兜底

例如最大金额 / 最小金额，只在没有更可靠信息时使用。

### 第四级：数学验证

```text
不含税金额 + 税额 ≈ 价税合计
```

误差建议 `<= 0.01`。

## 4. 文件名作为第二信息源

文件名可能包含：

- 日期
- 业务简称
- 金额

例如：

```text
2026.08.14-京东-128.50元.pdf
```

这些数据不应替代发票正文，但可以用于：

- 补充业务字段
- 金额交叉校验
- 后续用户自定义规则

## 5. 解析置信度

初始版本可以基于简单规则：

- 找到发票号：+0.25
- 找到开票日期：+0.15
- 找到三项金额：+0.30
- 金额校验通过：+0.20
- 找到销售方：+0.10

后续应根据真实发票样本逐步调整。

## 6. 低置信度处理

系统不能把低置信度结果伪装成成功。

低置信度结果应：

- `parseStatus = review`
- 高亮缺失字段
- 提供人工编辑
- P1 阶段提供 PDF 与字段并排复核
